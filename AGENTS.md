# AGENTS.md

Инструкции для ИИ-агентов и разработчиков в репозитории «Кабинет партнёра MultiFrame». Структура взята из [di-sukharev/vibe](https://github.com/di-sukharev/vibe), правила приспособлены к нашему составу: React + Vite (интерфейс), Node-функция без фреймворка (API), хранилище в S3.

## Рабочее соглашение

Владелец продукта (Павел) не программист. Он решает, что делать. Вы отвечаете за инженерные решения.

Общайтесь, ведите отчёты и пишите документы для владельца по-русски, коротко и по делу. Не заявляйте о проверках, которых не запускали. В отчёте перечислите: что изменено, какие проверки прошли, что упало, что нужно сделать владельцу.

## Состав репозитория

| Путь | Назначение |
| --- | --- |
| `apps/web` | Интерфейс: React 19, Vite, TypeScript. Сборка статики под `/cabinet`, режим PWA |
| `apps/api` | API: один обработчик (`index.js`), он же HTTP-сервер (`server.mjs`) и облачная функция. Данные платформы в хранилище S3 |
| `packages/shared` | Общий код и схемы для интерфейса и API: права ролей, телефон, проекты, справочник городов, схемы запросов |
| `e2e` | Проверка боевого сервера «только чтение» (Playwright) |
| `deploy`, `infra` | Docker, nginx, скрипты выпуска и откат, развёртывание в Yandex Cloud |
| `docs/handover` | Документы передачи: развёртывание, переменные, безопасность, резервные копии |
| `scripts` | Проверка границ архитектуры |

Подробности запуска и развёртывания — в [README](README.md) и [docs/handover](docs/handover/README.md). Не повторяйте их здесь и не заводите новый документ, если тема уже описана.

## Архитектура

Границы проверяет `npm run architecture:check`:

- `apps/web` не импортирует `apps/api`, `apps/api` не импортирует `apps/web`;
- `packages/shared` не импортирует приложения.

Всё, что нужно обеим сторонам (типы, правила, константы, справочники, схемы запросов), живёт в `packages/shared`. Не копируйте такие правила в приложения.

Схемы запросов лежат в `packages/shared/schemas.js` и собираются функцией `createSchemas(z)`: библиотеку zod передаёт вызывающий код. Так общий файл работает и в API (zod лежит в `apps/api/node_modules`, в архиве облачной функции и в образе Docker), и в интерфейсе. API берёт схемы из `apps/api/validation.js` (`parseBody`). Новое правило проверки добавляйте в схему, а не пишите вручную в обработчике. Тексты ошибок, статусы и пределы длины не меняйте без причины: интерфейс и тесты на них опираются.

Права по ролям описаны в одном месте: `packages/shared/rolePermissions.js`. Сервер закрывает всё, чего нет в списке разрешённого (403). Замерщик и монтажник цен не видят ни в списке, ни в карточке, ни в PDF.

Новый маршрут API: добавьте путь в `GATEWAY_PATHS` (`infra/deploy_yc.py`) и в [API_ROUTES](docs/handover/API_ROUTES.md), иначе на стенде будет 404.

## Команды

Нужен Node.js 22 (`.nvmrc`, поле `engines`). Установка: `npm run install:all`.

| Команда | Что делает |
| --- | --- |
| `npm run check` | Всё сразу: границы, lint, typecheck, тесты. Запускайте перед запросом на слияние |
| `npm run architecture:check` | Границы между `apps/web`, `apps/api` и `packages/shared` |
| `npm run lint` | Синтаксис API и eslint интерфейса |
| `npm run typecheck` | `tsc -b` для интерфейса |
| `npm test` | Тесты скриптов, API и интерфейса (vitest и `node --test`) |
| `npm run test:e2e --prefix apps/web` | Браузерные сценарии (Playwright). Нужен Chromium: `npx playwright install chromium` |

Запуск для разработки — [docs/handover/LOCAL_DEV.md](docs/handover/LOCAL_DEV.md).

## Тесты

Для изменения поведения и исправления ошибки сначала напишите тест и убедитесь, что он падает, затем правьте код. Для текста и стилей тесты не нужны.

- API: `node --test`, файлы `apps/api/*.test.js`. Обработчик вызывается напрямую или через локальный HTTP, хранилище подменяется файлом.
- Интерфейс: vitest и `tsx --test` рядом с кодом; браузерные сценарии в `apps/web/e2e`.
- Общие схемы: `apps/api/schemas.test.js`.
- Не запускайте тесты против боевого сервера. Набор `e2e` только читает и работает со стендом.

Не трогайте без отдельной просьбы владельца: тесты A-05, A-07, A-28, визуальные эталоны и эталонные скриншоты.

## Интерфейс

- Русский интерфейс без англицизмов: «проект», «комната», «замерщик», «монтажник», «коммерческое предложение». Подбирайте русские слова вместо заимствованных, ориентир — слова, уже употребляемые в кабинете. Исключение — названия, которые закреплены за продуктом (StP, MultiFrame, PDF).
- Доступность: у кнопок-значков есть `aria-label`, у полей ввода подписи, окна и ошибки получают `role="alert"` или `role="dialog"`, фокус виден (`:focus-visible`), анимации учитывают `prefers-reduced-motion`.
- Не показывайте ненастоящие данные в боевой сборке. Демо-режим только на стенде (`VITE_DISABLE_DEMO=1` в боевой сборке).
- Окончательную визуальную проверку выполняет владелец.

## Безопасность

- Секреты, ключи, пароли и персональные данные не попадают в Git, журналы, чат и отчёты. Файлы `.env` в `.gitignore`; в репозитории только `.env.example`.
- Не ослабляйте проверку входа, права ролей, ограничения частоты, проверку входных данных, заголовки безопасности и CORS.
- Токен входа подписан `JWT_SECRET` (HS256, 12 часов). Смену ключа делайте через `JWT_SECRET_PREVIOUS`, как описано в [SECURITY_CHECKLIST](docs/handover/SECURITY_CHECKLIST.md).
- Пароли только через `hashPassword` (bcrypt) и `passwordProblem` из `apps/api/security.js`.
- Не выводите значения переменных окружения и конфигурации облака. Не запускайте `yc config list`.
- Изменение, которое меняет, кто читает или меняет существующие данные, согласуйте с владельцем.

## Git

- Работайте в ветке (`cursor/...`, `feature/...`, `fix/...`) и открывайте запрос на слияние (PR) в `main`.
- Никогда не пушьте в `main` и не сливайте запрос без явного согласия владельца. Согласие на один запрос не распространяется на другие.
- Никакого принудительного пуша (force-push). Уже опубликованные метки не двигайте.
- Перед изменением состояния Git посмотрите статус и удалённые ветки. Чужую работу не удаляйте и не перезаписывайте.
- В запросе перечислите, что изменено, какие проверки прошли и нужны ли новые переменные окружения (имена, без значений). Не добавляйте в коммиты следы ИИ.
- Не трогайте запросы №1 и №12.

## Выпуск и развёртывание

- Слияние в `main` обновляет стенд владельца (GitHub Pages и функция Yandex Cloud) сам. Боевой сервер команды маркетинга обновляется только по метке `vX.Y.Z` на проверенной версии `main`.
- Метку ставит владелец или по его прямой просьбе. Порядок и шаблон сообщения — [OWNER_WORKFLOW](docs/handover/OWNER_WORKFLOW.md), [RELEASE](docs/handover/RELEASE.md), [STAGING_VS_PROD](docs/handover/STAGING_VS_PROD.md).
- Развёртывайте только по просьбе. Платные ресурсы облака подключает владелец.
- Не включайте на боевом сервере `DEMO_SEED` и `ALLOW_DEMO_RESET`.
- Миграции данных: если меняется формат документа платформы, сначала делайте его читаемым для старого формата, потом пишите в новом. Что будет изменено или удалено, объясните владельцу до выпуска.

## Сопровождение

- Чистый декларативный код. Удаляйте код, который ваши изменения сделали ненужным.
- Новые зависимости добавляйте, если без них не обойтись, выбирая популярные и поддерживаемые. После добавления в `apps/api` проверьте, что они попадают в архив функции (`infra/function_bundle.py`) и в образ Docker.
- Документируйте только решения, ограничения и порядок действий, не очевидные из кода. Дублирующие инструкции не пишите.
