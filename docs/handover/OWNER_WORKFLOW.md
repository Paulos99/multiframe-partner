# Для владельца: как внести изменение и выпустить версию

Короткая памятка Павла. Главное правило: **на боевой сервер идёт только метка, прошедшая стенд**.

```
изменить в личной ветке → стенд → проверить → метка vX.Y.Z → маркетинг ставит
```

## Шаги

1. **Правка в своей ветке.** Не в `main`. Имя вида `feature/что-делаем` или `fix/что-чиним`:
   ```bash
   git checkout main && git pull
   git checkout -b feature/название
   ```
   Правки, секреты и пароли в коммиты не попадают (демо-пароли лежат в закрытом файле, не в репозитории).
2. **Запрос на слияние (PR) в `main`.** Дождитесь зелёных проверок (API, интерфейс, смоук-тесты). Красное — чините в той же ветке, без принудительной перезаписи.
3. **Стенд.** После слияния стенд обновляется сам (GitHub Pages и функция Yandex Cloud), занимает до получаса. Адрес: https://paulos99.github.io/multiframe-partner/.
4. **Проверка на стенде.** Войдите «по логину» под ролями из закрытого файла демо-доступов: владелец, менеджер, замерщик, монтажник, администратор, менеджер StP.
   Пройдите свой сценарий, затем базовые: создать проект, открыть комнату, загрузить фото, собрать КП. Замерщик и монтажник цен не видят.
5. **Метка.** Если стенд в порядке, на той же проверенной версии `main`:
   ```bash
   git checkout main && git pull
   git tag -a v1.3.0 -m "Что изменилось"
   git push origin v1.3.0
   ```
   Автоматически запускается «Выпуск (по метке vX.Y.Z)»: проверки, сборка под `/cabinet`, архив и контрольная сумма на странице выпусков.
   Если проверки красные — выпуск не публикуется; исправьте через новую правку и метку с большим номером. Уже отправленную метку не переписывают.
6. **Сообщение маркетингу.** Номер метки, что изменилось, нужны ли новые переменные окружения (имена, без значений), меняется ли формат данных.
   Шаблон: «Выпуск v1.3.0: [что]. Новые переменные: нет. Данные: без изменений. Ставить: `./deploy/release.sh v1.3.0`».
7. **Маркетинг ставит.** `./deploy/release.sh v1.3.0`; при проблеме `./deploy/rollback.sh`. Подробнее — [RELEASE.md](RELEASE.md), [DEPLOY.md](DEPLOY.md).

## Если добавляете маршрут API

Добавьте путь в `GATEWAY_PATHS` (`infra/deploy_yc.py`) и обновите шлюз стенда, иначе на стенде он ответит 404. Занесите путь в [API_ROUTES.md](API_ROUTES.md).

## Чего не делать

- Не ставить метку на непроверенную ветку и не двигать выпущенные метки.
- Не включать демо на боевом сервере (`DEMO_SEED`, `ALLOW_DEMO_RESET`, `VITE_DISABLE_DEMO=1` должно остаться).
- Не отправлять пароли и значения переменных в чат, обращения и репозиторий.
- Новые демо-пароли: менять на стенде и в закрытом файле, публиковать не нужно.
