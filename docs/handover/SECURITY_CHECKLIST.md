# Чек-лист безопасности перед открытием для пользователей

Отметьте каждый пункт. Подробности и найденные проблемы — в [../SECURITY_AUDIT.md](../SECURITY_AUDIT.md).

## Сервер и сеть
- [ ] Сайт открывается только по **HTTPS** (сертификат действителен, HTTP перенаправляет на HTTPS).
- [ ] На внешнем прокси включён `Strict-Transport-Security: max-age=31536000; includeSubDomains` (после проверки, что HTTPS работает везде).
- [ ] Контейнер `web` слушает только `127.0.0.1` (наружу ходит внешний прокси); порт API (8080) наружу не открыт.
- [ ] Внешний прокси **перезаписывает** `X-Forwarded-For` (`$remote_addr`), а не дополняет клиентский заголовок: от этого зависит ограничение входа по адресу.
- [ ] На прокси включено ограничение частоты для `/cabinet-api/auth/login` (пример в [DEPLOY.md](DEPLOY.md)).
- [ ] Сервер обновляется (ОС, Docker), доступ по SSH — по ключам, вход под root запрещён.

## Секреты
- [ ] `JWT_SECRET` и `ANALYTICS_ADMIN_KEY` — случайные, ≥ 32 символов, разные, созданы именно для боевого сервера (не копии со стенда).
- [ ] `deploy/.env` с правами `600`, не в репозитории, не в чате и не в журналах. Резервная копия — в хранилище секретов.
- [ ] Ключ доступа к S3 — отдельный, права только на два бакета кабинета. Бакеты приватные, публичного чтения нет.
- [ ] `MATERIALS_BUCKET` отличается от `PARTNERS_BUCKET`; на бакете материалов настроен CORS только для `https://stp-multiframe.ru`.
- [ ] Включено версионирование бакета ([BACKUPS.md](BACKUPS.md)).
- [ ] Проверка хранилища `checkStorage.mjs` пройдена без ошибок ([SELF_HOST.md](SELF_HOST.md), шаг 4).
- [ ] Боевой кабинет не использует бакеты, ключи и пользователей стенда владельца.

## Режим «боевой»
- [ ] `DEMO_SEED` и `ALLOW_DEMO_RESET` **не заданы**; `NODE_ENV=production`.
- [ ] Сборка интерфейса с `VITE_DISABLE_DEMO=1` (по умолчанию в `deploy/`). Проверка: `https://stp-multiframe.ru/cabinet/?demo=1` не показывает переключатель ролей.
- [ ] Демо-логины (`admin`, `partner1`, `sales1`, `exec1`, `crew1` и т. п.) **не входят** в систему ни с какими паролями из разработки: проверить вручную. Пароли в репозиторий не записывать.
- [ ] Менеджер StP (`stp_manager`) видит только обучение и инструменты: на `/cabinet-api/admin/stp-managers` отвечает 403, без входа — 401 (не 404: путь опубликован в шлюзе, [API_ROUTES.md](API_ROUTES.md)).
- [ ] `ADMIN_BOOTSTRAP_*` удалены после создания администратора ([ADMIN_BOOTSTRAP.md](ADMIN_BOOTSTRAP.md)), пароль администратора сменён.
- [ ] `CORS_ORIGIN=https://stp-multiframe.ru` (без лишних адресов).
- [ ] `SHARE_LINK_TTL_DAYS` задан (рекомендуется 30).

## Проверки руками после установки
- [ ] Замерщик и монтажник **не видят цен** (ни в списке, ни в карточке, ни в PDF).
- [ ] Владелец компании А не видит объекты компании Б (проверить по прямой ссылке на объект).
- [ ] Ссылка для клиента открывается без входа и не показывает телефон, адрес, цены; отключённая ссылка отвечает «не найдено».
- [ ] 10 неверных паролей подряд блокируют вход на 15 минут.
- [ ] `curl -I https://stp-multiframe.ru/cabinet/` показывает `X-Content-Type-Options: nosniff` и `Content-Security-Policy-Report-Only`.
- [ ] `https://stp-multiframe.ru/cabinet/version.json` отвечает номером выпуска и не кэшируется.

## Политика CSP (рекомендация)
Контейнер `web` отдаёт `Content-Security-Policy-Report-Only`. Порядок перехода к рабочему режиму:
1. На стенде/на боевом сервере пройдите основные сценарии под каждой ролью с открытой консолью браузера: нарушения политики видны там.
2. Если нарушений нет (или добавлены нужные источники), владелец выпускает метку с `Content-Security-Policy` вместо `...-Report-Only` в `deploy/nginx/security-headers.conf`.
3. Следующий шаг усиления — убрать `'unsafe-inline'` из `script-src`: в `index.html` два встроенных скрипта, их разрешают хешами (`sha256-…`), это тоже выпуск владельца.

## Ротация и реагирование
- Плановая смена `JWT_SECRET`: новый ключ в `JWT_SECRET`, старый в `JWT_SECRET_PREVIOUS`, установка выпуска (`FORCE=1`); через 12 часов убрать `JWT_SECRET_PREVIOUS`, переустановить. Сессии не рвутся.
- Подозрение на утечку ключа: **не** кладите скомпрометированный ключ в `JWT_SECRET_PREVIOUS`; задайте новый — все сессии потребуют повторного входа.
- Смена `ANALYTICS_ADMIN_KEY` — независимо, без переходного периода. Ключи S3 — по регламенту (раз в 90 дней и при увольнении сотрудников с доступом).
- Утечка пароля пользователя: сброс пароля админом/владельцем завершает его сессии автоматически.
- Журнал: `docker compose logs api` — ошибки хранилища и блокировки входа (`login_locked` в журнале платформы).
