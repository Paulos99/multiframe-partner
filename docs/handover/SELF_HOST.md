# Кабинет целиком на своём сервере: порядок и проверка

Для команды, которая размещает кабинет у себя: интерфейс, API и хранилище, без обращений к серверам владельца.
Подробности по каждому шагу — в связанных документах, здесь только порядок и проверки.

## Что у вас своё, а что у стенда владельца

| | Ваш сервер (боевой) | Стенд владельца |
|---|---|---|
| Интерфейс | контейнер `web` на вашем сервере, адрес `https://stp-multiframe.ru/cabinet/` | GitHub Pages: `https://paulos99.github.io/multiframe-partner/` |
| API | контейнер `api` (`apps/api/server.mjs`), адрес `https://stp-multiframe.ru/cabinet-api/` | облачная функция Yandex Cloud за шлюзом |
| Хранилище | ваше S3-совместимое хранилище и два ваших бакета | бакеты владельца в Yandex Object Storage |
| Пользователи и данные | ваши, с нуля (первый администратор создаётся из `deploy/.env`) | тестовые демо-данные, сбрасываются |
| Секреты | `deploy/.env` на вашем сервере | секреты репозитория владельца |
| Когда меняется | когда вы ставите новую метку (`./deploy/release.sh vX.Y.Z`) | сразу после слияния в `main` |

Стенд и ваш сервер не связаны: общих бакетов, ключей, `JWT_SECRET` и пользователей нет. Поломка или сброс данных на стенде боевой сервер не затрагивает. Данные со стенда переносить **не нужно**: это тестовые данные.

## Порядок

1. **Сервер и прокси** — [DEPLOY.md](DEPLOY.md), разделы 0 и 2: Linux, Docker, внешний прокси с HTTPS для `/cabinet/` и `/cabinet-api/`.
2. **Хранилище.** Любое S3-совместимое (см. [DATA_LAYER.md](DATA_LAYER.md)). Создайте два **приватных** бакета (для кабинета и для материалов) и ключ с правами только на них. Требования:
   - условная запись `If-Match` / `If-None-Match: *` (на ней держатся документы платформы);
   - подписанные ссылки;
   - **адрес хранилища (`S3_ENDPOINT`) должен открываться из браузера пользователей по HTTPS**: ссылки на материалы подписываются этим же адресом, и браузер ходит по ним напрямую. Хранилище, доступное только внутри сервера, не подойдёт для материалов;
   - CORS на бакете материалов: `GET`, `HEAD`, `PUT` с `https://stp-multiframe.ru`, открытые заголовки `ETag`, `Content-Length`, `Content-Type`, `Content-Disposition`, `Accept-Ranges`.
   Какое именно хранилище выбрать — решение вашей команды. MinIO, Ceph RGW и облачные S3 российских провайдеров подходят по возможностям, но принимайте любое хранилище только после проверки `checkStorage.mjs` (шаг 4). Примечание: при проверке 29.10.2026 готовая сборка MinIO по адресу `dl.min.io` не скачивалась (ответ 410): учтите это при выборе.
3. **Настройки.** `cp deploy/.env.example deploy/.env`, `chmod 600 deploy/.env`. Заполните секреты (`openssl rand -hex 32`, каждый свой), `PARTNERS_BUCKET`, `MATERIALS_BUCKET`, `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, при необходимости `S3_FORCE_PATH_STYLE=1`, `CORS_ORIGIN=https://stp-multiframe.ru`, `ADMIN_BOOTSTRAP_*` (в `ADMIN_BOOTSTRAP_NAME` — имя и фамилия живого человека, не слово «Админ»). Названия всех переменных — [ENV.md](ENV.md). Значения не отправляйте владельцу и не публикуйте.
4. **Проверка хранилища до первого запуска:**
   ```bash
   cd /opt/multiframe-cabinet
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml run --rm --no-deps api node checkStorage.mjs
   ```
   Команда создаёт и удаляет только временные объекты `_check/…` в обоих бакетах и проверяет: запись, условную запись, чтение, подписанные ссылки, удаление. Ключей и паролей она не печатает. Все пункты должны быть с галочкой (код выхода 0); иначе исправляйте хранилище, а не кабинет.
   Затем проверьте CORS руками из браузера (раздел «Материалы» после первого входа: загрузка файла и просмотр).
5. **Установка:** `./deploy/release.sh v1.0.0` (подставьте метку из раздела «Выпуски» на GitHub). Скрипт сам проверяет `/cabinet/version.json` и `/cabinet-api/health`.
6. **Первый администратор** — [ADMIN_BOOTSTRAP.md](ADMIN_BOOTSTRAP.md): войти, сменить пароль, убрать `ADMIN_BOOTSTRAP_*` из `deploy/.env`, `FORCE=1 ./deploy/release.sh <метка>`.
7. **Безопасность и копии** — [SECURITY_CHECKLIST.md](SECURITY_CHECKLIST.md), [BACKUPS.md](BACKUPS.md). Включите регулярные копии бакетов до того, как в кабинете появятся реальные данные.
8. **Яндекс.Метрика (по желанию).** Номер счётчика — в `deploy/.env`: `VITE_YM_ID=<цифры>`, затем `FORCE=1 ./deploy/release.sh <текущая метка>` (интерфейс пересоберётся с этим номером). Скрипт Метрики и баннер согласия появляются только когда номер задан и только после согласия посетителя. Доступ к счётчику выдайте владельцу (логин `pavel199975`, роль «Просмотр»).

## Свои дополнения к запуску

Файл `deploy/docker-compose.override.yml` (на сервере, не в репозитории; шаблон — `deploy/examples/docker-compose.override.example.yml`) подключается скриптом `release.sh` автоматически. Через него добавляют тома (адаптер PostgreSQL по [DATA_LAYER.md](DATA_LAYER.md)) и свои заголовки безопасности.

Если хранилище не на `storage.yandexcloud.net`: политика CSP в контейнере `web` работает в режиме наблюдения (Report-Only) и **не блокирует** загрузку, но в консоли браузера покажет нарушения. Чтобы их не было, смонтируйте свою копию `security-headers.conf` с адресом вашего хранилища в `img-src`, `connect-src` и `media-src` (пример — в файле-шаблоне). Перед переводом политики в рабочий режим ([SECURITY_CHECKLIST.md](SECURITY_CHECKLIST.md)) это обязательно.

## Что делать при выпуске новой версии

`./deploy/release.sh vX.Y.Z` — данные не затрагиваются, откат — `./deploy/rollback.sh`. Владелец сообщает, нужны ли новые переменные в `deploy/.env`.
