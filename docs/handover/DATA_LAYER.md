# Слой данных: как устроено хранение и как подключить свою базу

## Главное

- **YDB в коде нет, SQL-базы тоже.** Всё состояние платформы — один JSON-документ `platform-v2.json`
  (плюс `analytics-events.json` для событий) в S3-совместимом хранилище. Фото, PDF и материалы — отдельные объекты.
- Доступ к хранилищу сосредоточен в двух файлах:
  - `apps/api/objectStore.js` — низкоуровневый доступ (чтение, запись с условием, удаление, подписанные ссылки);
  - `apps/api/platformStore.js` — документ платформы: кэш, проверка версии (ETag), запись с `If-Match`
    и трёхстороннее слияние при одновременных изменениях.
- Сервис можно перевести на свою базу **без правки кода**, подключив адаптер переменной окружения
  `DOCUMENT_STORE_MODULE` (раздел «Своя база данных»). Файл адаптера хранится у вас.

## Что где лежит

| Что | Где | Ключ |
|---|---|---|
| Данные платформы: пользователи, компании, объекты, проекты, журнал, ссылки клиентов, материалы | бакет `PARTNERS_BUCKET` | `platform-v2.json` |
| События аналитики | `PARTNERS_BUCKET` | `analytics-events.json` |
| Фотографии комнат | `PARTNERS_BUCKET` | `photos/<компания>/<объект>/<id>.jpg` (и миниатюры рядом) |
| PDF документы объектов | `PARTNERS_BUCKET` | `docs/<компания>/<объект>/<id>.pdf` |
| Методические материалы (файлы, видео) | `MATERIALS_BUCKET` | по структуре папок материалов |

Бакеты приватные. Фото открываются только по подписанной ссылке API (`/photo-file/<id>?v=..&e=..&s=..`,
подпись HMAC, действует 10 минут, привязана к фото и сроку). Материалы — по подписанным ссылкам хранилища (чтение 15 минут,
загрузка 1 час, выдаются только админу).

## Схема документа `platform-v2.json`

```
{
  "version": 2,
  "users":      [ { id, login, passwordHash (bcrypt), role, displayName, orgId|null, createdAt,
                    sessionVersion, lockedUntil?, avatarKey? } ],
  "orgs":       [ { id, createdAt, createdBy, settings: { companyName, city, panelPriceRub, pricePerM2,
                    installPricePerM2, dowelsPerPanel, dowelPriceRub } } ],
  "objects":    [ { id, orgId, projectId, createdAt, updatedAt, createdBy, assignedTo, status,
                    clientName, clientPhone, address, city, room, estimate, clientSummary,
                    history[], documents[], photos[] } ],
  "projects":   [ { id, orgId, name, clientName, clientPhone, address, city, createdAt, updatedAt, createdBy } ],
  "activity":   [ { id, at, orgId, userId, login, action, detail } ],
  "roomShares": [ { id: "shr_<id комнаты>", token, enabled, snapshot, createdAt, updatedAt } ],
  "materials":  [ папки и файлы методических материалов ]
}
```

Роли: `admin` (orgId = null), `owner`, `sales`, `measurer`, `crew`. Логин уникален (без учёта регистра).
Пароли хранятся только как bcrypt-хеш. Цены (`estimate`) отдаются замерщику и монтажнику в урезанном виде:
это делает сервер (`packages/shared/projectAccess.js`, `estimateForRole`).

Ограничения размера, заложенные в код: до 5000 объектов, 500 записей журнала, 5000 событий аналитики; в одном объекте
до 50 записей истории, 40 документов, 60 фото. Документ целиком читается и пишется на каждое изменение — подход рассчитан
на сотни компаний, а не на миллионы записей.

`analytics-events.json`: массив событий `{ id, at, type, orgId, userId, role, ... }`. Личность в событии берётся
из токена сессии, а не из тела запроса (для анонимных обращений личность не сохраняется).

## Вариант 1. Другое S3-хранилище (самый простой)

Нужно только окружение, код не меняется:

```
S3_ENDPOINT=https://s3.ваш-провайдер.ru
S3_REGION=ru-1
S3_ACCESS_KEY_ID=...   S3_SECRET_ACCESS_KEY=...
S3_FORCE_PATH_STYLE=1        # для MinIO и части провайдеров
PARTNERS_BUCKET=...  MATERIALS_BUCKET=...
```

Проверить хранилище на соответствие требованиям до первого запуска можно командой из [SELF_HOST.md](SELF_HOST.md) (шаг 4, `checkStorage.mjs`).

Требования к хранилищу:
- условная запись `PutObject` с `If-Match` и `If-None-Match: *` (на этом держится защита от потери данных при
  одновременных изменениях; MinIO, Ceph RGW и Yandex Object Storage поддерживают; если ваше хранилище не поддерживает —
  используйте вариант 2 для документов);
- подписанные ссылки (presigned) для чтения и записи. Они подписываются адресом `S3_ENDPOINT`, поэтому он должен открываться и с сервера API, и из браузера пользователя (HTTPS);
- CORS на бакете материалов для браузера: разрешить `GET`, `HEAD`, `PUT` с `https://stp-multiframe.ru`,
  открыть заголовки `ETag`, `Content-Length`, `Content-Type`, `Content-Disposition`, `Accept-Ranges`.
  (Скрипт `infra/set_materials_bucket_cors.mjs` написан под Yandex и стенд владельца — на ваше хранилище настройте CORS его средствами.)
- бакеты приватные, ключ сервиса имеет права только на эти два бакета.

## Вариант 2. Своя база данных для документов (PostgreSQL и другие)

Адаптер — объект с тремя операциями над двумя ключами (`platform-v2.json`, `analytics-events.json`):

| Метод | Что делает |
|---|---|
| `handles(key)` | `true` для ключей, которые хранит ваша база |
| `head({ key })` | `{ missing, etag }` — версия документа без чтения тела |
| `read({ key })` | `{ missing, body, etag }` — текст JSON и его версия |
| `put({ key, body, ifMatch, ifNoneMatch })` | записывает и возвращает `{ etag }`. Если `ifMatch` не совпал с текущей версией или документ уже есть при `ifNoneMatch: '*'`, бросает ошибку со `status: 412` |

`etag` — любая строка-версия (в примере MD5 в кавычках). Главное требование — **атомарность проверки версии и записи**
(в SQL: `UPDATE ... WHERE etag = $старый`, проверить число затронутых строк). Без неё два одновременных изменения
затрут друг друга.

Готовый пример для PostgreSQL: [examples/postgres-document-store.mjs](examples/postgres-document-store.mjs).
Как подключить:

```bash
# deploy/.env
DOCUMENT_STORE_MODULE=/adapters/postgres-document-store.mjs
DATABASE_URL=postgres://...
```

и смонтируйте каталог с адаптером и зависимостью `pg` в контейнер `api` (том в `docker-compose.override.yml`,
который лежит у вас на сервере, а не в репозитории), либо соберите свой образ `FROM` нашего с `npm i pg`.
Бакет `PARTNERS_BUCKET` всё равно нужен: в нём фото и PDF.

Контракт проверяется тестом `apps/api/documentStore.test.js` (адаптер «в памяти»): запустите его логику против своей базы,
подставив ваш адаптер.

## Вариант 3. Полностью реляционная схема (отдельный проект)

Если нужны таблицы `users`, `orgs`, `objects` и т. д. с запросами и индексами, придётся переписать `platformStore.js` и места,
где `index.js` читает и записывает массивы платформы. Это не конфигурация, а доработка: поручите её владельцу репозитория,
чтобы код оставался в одном месте и выпускался метками. Практичный путь: начать с варианта 2, а таблицы выделять поэтапно.

## Файлы (фото, PDF) без S3

Файлы требуют S3-совместимого хранилища (подписанные ссылки, multipart-загрузка видео). Заменить его файловой системой
без доработки кода нельзя. Любое S3-совместимое хранилище (MinIO на своём сервере) подходит.

## Перенос текущих данных со стенда (обычно не нужен)

Данные стенда владельца — тестовые. Боевой кабинет начинают с чистого хранилища и первого администратора ([ADMIN_BOOTSTRAP.md](ADMIN_BOOTSTRAP.md)). Перенос нужен только если владелец отдельно попросит вас сохранить данные.

1. Остановите запись на стенде (или договоритесь о времени).
2. Скопируйте объекты бакета стенда в ваше хранилище (`rclone sync` или `aws s3 sync --endpoint-url ...`).
3. Для варианта 2 загрузите `platform-v2.json` и `analytics-events.json` в таблицу `mf_documents`.
4. Проверьте вход администратором и несколько объектов с фото.
Пароли переносятся как есть (bcrypt). Секрет `JWT_SECRET` на новом месте — **новый**; сессии стенда не переносятся.
