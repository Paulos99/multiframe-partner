# Стенд и боевой сервер: порядок выпуска изменений

## Два окружения

| | Стенд владельца (Павла) | Боевой: https://stp-multiframe.ru/cabinet |
|---|---|---|
| Где | GitHub Pages + Yandex Cloud (функция + шлюз + Object Storage) | сервер команды интернет-маркетинга |
| Кто видит | только владелец | пользователи |
| Данные | тестовые, могут сбрасываться; демо-режим включён | реальные; демо отключено (`VITE_DISABLE_DEMO=1`, без `DEMO_SEED`) |
| Как обновляется | автоматически при каждом изменении ветки `main` (рабочие процессы GitHub) | командой установки по метке выпуска |
| Секреты | свои (GitHub Secrets стенда) | свои (`deploy/.env` на сервере). **Общих секретов нет** |

Окружения не делят ни ключи, ни бакеты, ни `JWT_SECRET`: утечка со стенда не открывает боевые данные.

## Как владелец вносит изменения (процесс для Павла)

1. Правки делаются в ветке (например `cursor/...` или `feature/...`) и открывается запрос на слияние (PR) в `main`.
   Проверки (API, интерфейс) должны пройти.
2. Запрос сливается в `main` → стенд обновляется сам. Проверка на стенде: вход под каждой ролью, нужный сценарий,
   `?demo=1`. Видит только владелец.
3. Если на стенде всё хорошо, владелец ставит метку выпуска на **ту же** проверенную версию `main`:
   ```bash
   git checkout main && git pull
   git tag -a v1.3.0 -m "Что изменилось"      # желательно с подписью: git tag -s
   git push origin v1.3.0
   ```
   Рабочий процесс `Выпуск` (`.github/workflows/release.yml`; до переноса файл лежит в `deploy/github-workflows/`) повторно проверяет код, собирает статику под `/cabinet`
   и публикует выпуск на GitHub с архивом и контрольной суммой.
4. Владелец сообщает команде: «Выпуск v1.3.0, [что изменилось, нужны ли действия: новые переменные, миграция]».
5. Команда устанавливает: `./deploy/release.sh v1.3.0` (или запускает свой процесс — `deploy/examples/deploy-over-ssh.yml`).
6. Если что-то пошло не так — `./deploy/rollback.sh` (на предыдущую метку; подробнее в [DEPLOY.md](DEPLOY.md)).

Метка = неизменяемая версия кода. На сервер попадает только то, что прошло шаги 1–3.

## Правила, чтобы не ломать боевой сервер

- Нельзя слать на боевой сервер непроверенные ветки: скрипт принимает только метки, лежащие на `main`.
- Новые переменные окружения: владелец перечисляет их в описании выпуска; команда добавляет в `deploy/.env` **до** установки.
- Изменения формата данных (если появятся) — отдельной строкой в описании выпуска и с копией данных перед установкой
  ([BACKUPS.md](BACKUPS.md)).
- Версионируйте по смыслу: `v1.3.1` — исправление, `v1.4.0` — новая возможность, `v2.0.0` — требует действий команды.
- На стенде можно включать `DEMO_SEED=1` и `ALLOW_DEMO_RESET=1` (переменные GitHub Actions `DEMO_SEED`, `ALLOW_DEMO_RESET`); на боевом их не бывает.

## Рекомендуемые настройки репозитория (делает владелец)

- Защита ветки `main`: обязательные проверки перед слиянием, запрет прямой отправки и принудительной перезаписи.
- Защита меток `v*`: создавать могут только владельцы (Settings → Rules → Rulesets).
- Подписывать метки выпусков; команда включает `REQUIRE_SIGNED_TAG=1` после того, как получит публичный ключ владельца.
