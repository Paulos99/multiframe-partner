# ADR-005 — Пресеты сегмента потолочников; два типа расчётов комнаты

- **Статус:** Accepted (`rev-gate-a-approved-20261022`)
- **Дата:** 2026-10-22

## Контекст

Клиент партнёра пришёл за натяжным потолком. PRODUCT_SPEC проблемомера (visitor) спрашивает тип потолка и строит «следующий шаг» под публичную конверсию. Калькулятор содержит стены. Алгоритмы акустики и раскладки удалять нельзя.

В draft-1 area-режим **не** сохранялся в комнату (`AreaPreview → Abandoned` без SaveToRoom). На практике менеджеру нужен **предварительный** расчёт по площади для консультации и раннего КП-черновика — без полной схемы. Молчаливый запрет save создавал разрыв «посчитал — некуда положить».

## Решение

### A. Пресеты сегмента (без изменений сути draft-1)

В **партнёрском** пути сегмента «потолочники»:

1. PM формирует потребность в ЗИ; не требует входную жалобу на шум.  
2. Вопрос типа потолка убрать из **основного** UI-пути; для модели — пресет «натяжной» / скрытые параметры.  
3. «Следующий шаг» = действия с project/room context (или quick-entry → привязка, ADR-007).  
4. Стены **вне основного UI** калькулятора; код wall-* не удалять.

### B. Два типа расчётов у комнаты

Оба принадлежат **комнате**; различаются точностью, назначением и готовностью к КП.

| Тип | Вход | Что сохраняется | Назначение | Готовность к КП |
|-----|------|-----------------|------------|-----------------|
| **preliminary** | площадь (и опц. простые параметры) | estimate по площади; **без** схемы/BOM раскладки | консультация, ориентир цены, ранний черновик / КП | только как «предварительно»; **не** = tech-ready для бригады |
| **detailed** | геометрия + схема + спецификация | схема, BOM, document `estimate` со схемой | точная смета, tech-ready, монтаж, финальное КП | да — основной источник для КП и бригады |

Правила:

1. Save **обоих** типов — явный CTA «Сохранить в комнату X» / quick-entry: Save → bind → persist (не silent orphan).  
2. На комнате могут сосуществовать preliminary и detailed; UI различает бейджами/подписями.  
3. **Запрет двойного суммирования:** в предварительном итоге проекта, в **новых** КП и в аналитике сумм **нельзя** складывать preliminary + detailed одной и той же комнаты. Правило агрегации: если есть `detailed` — в сумму/КП идёт он; иначе — `preliminary` (с пометкой «предварительно»).  
4. Area ≠ раскладка: копирайт и empty/warning states обязаны это говорить.  
5. **Согласие на покупку ≠ готовность к монтажу:** preliminary в КП ок; перед install обязательны актуальный detailed, материалы, ответственный (D1 §5.6).  
6. Изменение calc **не** меняет уже `sent_confirmed` QuoteRevision → новая версия (ADR-004).  
7. Crew видит **техсмету с ценами**; не видит клиентское КП / коммерческий итог проекта.

Детальные поля, snapshot Quote и копирайт — D5/D6/D7 (Gate B), не в этом ADR.

## Отвергнутые альтернативы

| Альтернатива | Почему нет |
|--------------|------------|
| Оставить полный visitor questionnaire в кабинете | Трение и ощущение «не для потолочников» |
| Удалить wall-алгоритмы | Нужны другим сегментам / future |
| Всегда создавать новый объект при save из Tools | Потеря иерархии проекта (разрыв B1) |
| Считать area-save полноценной сметой | Ложная точность раскладки |
| Запретить persist preliminary (draft-1) | Ломает консультацию и ранний ориентир; данные теряются |
| Суммировать оба типа в итоге проекта | Двойной учёт одной комнаты |

## Следствия

- IA tools всегда с room picker, deep-link из комнаты, или quick-entry → bind (ADR-007).  
- State diagram Calculation: ветка SavePreliminaryToRoom + SaveDetailedToRoom.  
- Академия/справка объясняют preliminary vs detailed.  
- D1 иерархия: у комнаты `calculation.preliminary` и `calculation.detailed`.
