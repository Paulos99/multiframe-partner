## 1. Решения, утверждённые владельцем (canonical)

| ID | Утверждённое правило | Ссылки |
|---|---|---|
| **A-06** | После выполнения заказанных (`ordered`) комнат сделку **явно закрывает sales или owner**; `room.closed` не закрывает Deal автоматически. `accepted` = факт продажи, не факт монтажа. | D5 §3.1, D8 |
| **A-09** | **Гибридное продвижение стадий:** первый пригодный PM → `assessed`, первый сохранённый расчёт → `calculated`, `confirm_sent` → `quote_sent_confirmed`; коммерческое решение (accepted/declined/early pause/decline) фиксируется **только вручную**, без выдуманных исходов. | D5 §3.1, D6–D8 |
| **A-11** | **Атомарное создание** Project+Room+active Deal с `Idempotency-Key`; повторная отправка не создаёт дублей, quick-entry draft до bind не создаёт Deal. | D5 §3.1 |
| **A-12** | Для расчётов — **append-only CalculationRevision** и optimistic concurrency (`expectedRevision`/`ETag`, конфликт `409`), сохранение обеих веток и явное разрешение конфликта. Silent last-write-wins запрещён. | D5 §1.8, D7 |
| **Pause-canon** | `early_paused` — **нетерминальная пауза**; Deal остаётся active, возобновление в той же Deal с тем же `dealId`; пауза не считается проигранной продажей. `early_declined` — терминальный отказ. | D3 §5.5, D5, D8, D10 |
| **M-assent** | При миграции **отправленное КП ≠ подтверждённый заказ**. `ordered` только при доказанном принятии и составе; иначе `unknown` / `needs_review` без попадания в суммы подтверждённых заказов и монтажный пул. | D5 §4, D11 |

Эти шесть решений имеют статус **resolved / owner-approved**. Gate A (Project→Rooms, ADR-008, quote immutability, sequential deals) сохраняется без изменений.

## 2. Не входило в утверждение (не выдавать за owner-approved)

- **A-05:** исключения из монтажного чек-листа / waiver; предлагается owner + reason — **пока не утверждено**, зафиксировать до реализации соответствующих действий.
- **A-07:** подтверждение отправки КП без указания канала — **пока не утверждено**, согласовать до реализации.
- **A-28:** пороги сигналов StP — пилотная калибровка.
- Прочие nonblocking assumptions не становятся автоматически утверждёнными.

## 3. Gate C — РАЗРЕШЁН, строго ограниченный периметр

Разрешено **создавать самостоятельные интерактивные HTML-прототипы** desktop и mobile и готовить UX-тесты на основе утверждённых D3–D11. Требуется показать работающие сценарии всех пяти ролей (admin StP, owner, sales, measurer, crew), навигацию, ключевые состояния, сохранение/привязку расчёта, сделки и КП, монтажный чек-лист, Академию и StP-контур. Проверять сценарии и критерии [D11 §7](./11-acceptance-matrix.md), особенно понятность «без инструкций», незаметность лишних действий, anti-loss, отсутствие перегруженных домашних экранов.

**Разрешение Gate C не означает Gate D.** Запрещены:
- изменения или реализация production `apps/*`, `packages/*`, API, БД и миграций;
- merge PR #78 в main, деплой, изменение прав действующих пользователей или существующих данных;
- объявлять демо-фикстуры прототипа доказательством работы production.

Прототипы хранить **изолированно** (например, `docs/partner-ux-prototypes/`) в текущей рабочей ветке/PR #78, не смешивая с исполняемым приложением. Публиковать ссылки, подробные переходы и чек-листы тестирования в PR #78. Перед Gate D — отдельная приёмка прототипов и явное решение владельца.
