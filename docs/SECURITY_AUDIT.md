## Высокая

**S-01. Аналитика читалась без входа** — `apps/api/index.js`, `GET /analytics/dashboard`.
Без токена роль и компания принимались из заголовков `X-Analytics-Role` и `X-Analytics-Org`; по ним отдавалась сводка любой компании.
Исправлено: без входа допускается только служебный запрос с ключом `ANALYTICS_ADMIN_KEY` (сравнение за постоянное время),
роль и компания берутся только из токена. Тест: `securityHardening.test.js`.

**S-02. Демо-данные и администратор с известным паролем в любом пустом хранилище; сброс боевых данных** — `index.js`
(`defaultPlatform`, `/admin/demo/reset`). Пустой бакет (или потеря объекта) автоматически поднимал демо-кабинеты с паролями,
опубликованными в README; администратор мог одной командой затереть данные демо-набором.
Исправлено: демо поднимается только при явном `DEMO_SEED=1` либо локально (без бакета и вне `NODE_ENV=production`);
пустое боевое хранилище создаёт единственного администратора из `ADMIN_BOOTSTRAP_*` (пароль ≥ 10 символов) или отвечает 503 с подсказкой;
`/admin/demo/reset` при заданном бакете отвечает 403, пока не задан `ALLOW_DEMO_RESET=1`; миграция старого файла не задаёт пароль `admin1234`.
Тесты: `bootstrapStorage.test.js`, `securityHardening.test.js`.
*Для стенда владельца:* данные в бакете стенда не затронуты. Чтобы на стенде работал сброс к демо или поднимался демо-набор,
задайте переменные Actions `ALLOW_DEMO_RESET=1` / `DEMO_SEED=1` (передаются деплоем: `infra/function_env.py`).

**S-03. Уязвимые зависимости интерфейса: DOMPurify (критическая рекомендация), vite, source-map-js** — `apps/web/package-lock.json`.
`npm audit fix` без смены мажорных версий (изменён только lock-файл): остались 6 замечаний низкой и средней важности (см. S-28). API: 0 замечаний.
Исправлено; проверено сборкой, типами, линтером и тестами.

## Средняя

**S-04. XSS в калькуляторе через подписи и идентификаторы стен** — `apps/web/public/calculator/src/{ui/app.js,core/room-model.js,editor/opening-tool.js,export/pdf-export.js}`.
Подписи стен, идентификаторы и числа из импортируемого состояния вставлялись в `innerHTML` без экранирования.
Исправлено: `core/html-escape.js` (`escapeHtml`, `safeId`, `safeLabel`), числа приводятся к числам, состояние при загрузке очищается.
Тест: `apps/web/src/partner/calculatorXss.test.ts`. Файлы `calculator/app.js`, `calculator.js`, `visualizer.js` в корне каталога калькулятора — старая версия, из `index.html` не подключена (удалять не стали, чтобы не трогать лишнее).

**S-05. Подмена личности в событиях аналитики** — `POST /analytics/events`. Любой без входа мог писать события от имени любой компании и роли.
Исправлено: при наличии токена личность берётся из токена; без токена — анонимное событие без личности. Клиент (`apps/web/src/partner/analytics.ts`) теперь отправляет токен.

**S-06. Нет защиты входа от перебора** — `POST /auth/login`. Исправлено: блокировка записи на 15 минут после 10 неверных паролей
(счётчик хранится в данных, общий для экземпляров), ограничение 30 попыток за 10 минут с одного адреса, ответ 429 с `Retry-After`.
Ограничение по адресу хранится в памяти экземпляра: на боевом сервере добавьте ограничитель на внешнем прокси (пример в DEPLOY.md).

**S-07. Слабая политика паролей** — создание партнёров/сотрудников и сброс. Принимался любой непустой пароль. Исправлено: от 10 символов, до 72 байт (предел bcrypt), без пробелов по краям.
Уже существующие слабые пароли (демо-учётные записи) — действие: сменить (см. S-27).

**S-08. Токен подходил новой записи с тем же логином** — `requireAuth`. Пользователь искался и по идентификатору, и по логину из токена. Исправлено: только по идентификатору.

**S-09. Сброс пароля не завершал сессии** — сброс пароля партнёра/сотрудника. Исправлено: `sessionVersion` увеличивается, старые токены перестают работать; счётчики блокировки сбрасываются.

**S-10. Недостаточная проверка при записи объектов** — `PATCH/POST /objects`. `assignedTo` принимал любой идентификатор (в том числе пользователя другой компании);
идентификатор комнаты от клиента не проверялся; размеры строк и расчёта не ограничивались. Исправлено: исполнитель обязан быть из той же компании и с подходящей ролью;
идентификатор — `[A-Za-z0-9_-]{1,64}`; ограничения длины; расчёт ≤ 400 КБ. Остальные маршруты (объекты, проекты, фото, документы, материалы, профиль, ссылки клиентов)
просмотрены на IDOR: доступ везде идёт через `objectVisibleTo`/роль, цены вырезаются на сервере (`estimateForRole`) — дополнительных нарушений не найдено (покрыто `staffAccess.test.js`, `documentAccess.test.js`).

**S-11. CORS** — единственный жёстко заданный адрес по умолчанию (стенд владельца). Исправлено: список адресов в `CORS_ORIGIN`, ответ одним совпавшим адресом, `Vary: Origin`, без `*`.
Действие при размещении на своём сервере: `CORS_ORIGIN=https://stp-multiframe.ru` (в шаблоне `deploy/.env.example` есть). Для стенда: оставить адрес Pages.

**S-12. Нет заголовков безопасности API; внутренности в ответах 500** — исправлено: `X-Content-Type-Options`, `Referrer-Policy`, `Content-Security-Policy: default-src 'none'`, `Strict-Transport-Security`, `X-Frame-Options`;
500 отвечает общим текстом, подробности только в журнале сервера.

**S-13. Злоупотребление записью аналитики** — без ограничений по объёму и частоте. Исправлено: до 100 событий за запрос, 60 запросов в минуту с адреса, поля обрезаются, вложенный объект ≤ 2 КБ, время события ограничено разумным диапазоном; общий предел тела запроса `MAX_BODY_BYTES`.

**S-14. Ссылка для клиента без срока жизни** — `roomShare.js`. Добавлено `SHARE_LINK_TTL_DAYS` (в шаблоне боевых настроек 30), заголовок `X-Robots-Tag: noindex, nofollow`.
Проверено: публичный ответ собирается по белому списку полей; телефона, имени клиента, адреса, цен, сотрудников и компании в нём нет. Токен — 192 бита из `crypto`; неизвестная, выключенная и просроченная ссылки отвечают одинаково (404).

**S-15. Ключи и секреты — проверка владельцем.** *Действие владельца.* В истории и в рабочей копии настоящих секретов не найдено (только тестовые значения; см. I-02).
Но `docs/security.md` описывает прежнюю утечку вычислимого ключа подписи и ключа аналитики. Убедитесь, что на стенде `JWT_SECRET` и `ANALYTICS_ADMIN_KEY` — случайные значения ≥ 32 символов, заданные после той утечки
(деплой отказывается использовать старое производное значение и короткие ключи: `infra/function_env.py`). Боевой сервер получает **новые** независимые секреты (создаёт команда размещения), общих секретов со стендом быть не должно.
Ключи сервисных аккаунтов стенда команде не передаются.

**S-16. Ветка `main` не защищена** (`gh api …/branches/main/protection` → 404). *Действие владельца.* Включите обязательные проверки, запрет прямой отправки и принудительной перезаписи, защиту меток `v*` —
по `main` и меткам команда размещения устанавливает код.

- **S-21.** bcrypt cost 10, синхронный. Исправлено: cost 12 (`BCRYPT_COST`, 10–14), асинхронно; старые хеши продолжают работать.
- **S-22.** `deploy-api.yml` без блока `permissions` (права по умолчанию). Исправлено в виде патча `deploy/github-workflows/deploy-api.yml.patch` (`contents: read`); применить вручную владельцем (см. deploy/github-workflows/README.md). Остальные процессы уже ограничены (`deploy.yml` — права Pages, `e2e-smoke.yml` — ручной запуск). Репозиторий: права токена по умолчанию «только чтение».

- **S-24.** Токен сессии хранится в `localStorage` (`mf_partner_token_v1`) — при XSS его можно украсть. *Принято:* переход на httpOnly-куки — переработка клиента и CORS. Смягчение: экранирование (S-04), срок 12 часов, `sessionVersion`, CSP (рекомендуется довести до рабочего режима, см. SECURITY_CHECKLIST.md).
- **S-25.** Подпись временных ссылок на фото использует `JWT_SECRET` (смена ключа обрывает такие ссылки на ≤ 10 минут). *Принято.*
- **S-26.** Сторонние действия GitHub (`actions/*`) закреплены по версии, а не по SHA коммита. *Принято;* при желании закрепите по SHA.
- **S-27.** В `README.md` (репозиторий открытый) и в подсказке на экране входа были опубликованы логины и пароли демо-кабинетов, в том числе администратора, и они работали на стенде. Исправлено: на стенде все пароли заменены новыми (старые отвечают 401), а демо-пользователи и данные пересозданы; пароли из `README.md` и с экрана входа удалены, новые лежат только в закрытом файле владельца и в репозиторий не попадают. На боевом сервере демо-записи не создаются (S-02). Остаётся: пароли разработки в `apps/api/demoSeed.js` и `apps/web/src/partner/demoSeed.ts` (годятся только для локального запуска; серверные записи с ними при `DEMO_SEED=1` создаются только на стенде и компьютере разработчика). Администратору стенда выдан временный пароль, приложение не требует смены при первом входе: сменить в профиле сразу.
- **S-28.** Остались 6 замечаний `npm audit` (4 низких, 2 средних): `exceljs → uuid` (ошибка только при передаче буфера в `uuid` v3/v5/v6 — наш код так не вызывает), цепочка `vite-plugin-pwa → workbox-build → …` (сборочные зависимости).
  Исправление требует несовместимых обновлений. *Принято;* пересмотреть при ближайшем обновлении зависимостей.
