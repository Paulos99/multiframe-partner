# План развития MultiFrame на 18 октября 2026

**Актуальный план по новому поручению Павла. Заменяет прежний ограниченный объём дня.**

Павел — заказчик. ChatGPT/Codex — интерфейс, сценарии и клиентская интеграция. Грокбот «Мультифрейм партнёр» — сервер, хранение, доступы, материалы и управление агентами Cursor. Работа параллельная, без ожидания взаимных устных отчётов. Обязательные точки взаимодействия — изменение контракта данных, конфликт файла, блокер интеграции.

## 1. Результат, к которому идём сегодня

Рабочий проект «Квартира» с несколькими помещениями. Каждое помещение сохраняет диагностику, замер, расчёт и документы. Из проекта доступны комнаты, общий предварительный итог и следующий шаг. Каждый сотрудник видит подходящую его роли рабочую страницу.

Основной проверочный сценарий: менеджер создаёт проект с тремя комнатами → выполняет диагностику комнаты → калькулятор получает известную площадь → расчёт сохраняется в нужную комнату → владелец видит состав и итог проекта → замерщик получает назначенную комнату → монтажник получает своё задание и спецификацию без цен.

Это целевой объём, не обещание готовности всех пунктов к фиксированному часу. В конце дня отдельно называются реально работающие сценарии и незавершённые части. Новые возможности показываются как рабочие только после серверной интеграции.

## 2. Как вводим проекты без потери старых данных

- Существующий `JobObject` сохраняем как запись помещения: прежний id, ответы, смета, PDF, история и назначение не переписываются миграцией.
- Добавляем сущность проекта с клиентом, адресом и компанией. В помещение добавляем необязательные `projectId` и `roomName`.
- Старые объекты без проекта продолжают открываться в разделе «Без проекта». Пользователь может явно добавить их в проект.
- Никакой автоматической группировки по совпадению телефона, имени или адреса: это может объединить разных клиентов.
- Проект принадлежит одной компании. Присоединять можно только помещения той же компании с проверкой полномочий на сервере.
- В проекте показываем количество помещений, известную площадь, состояние расчётов и следующий шаг. Итог помечаем «предварительный», пока не сохранено отдельное предложение.
- Нерассчитанная комната не считается нулевой: показываем «Рассчитано 2 из 3 помещений» и неполноту итога.
- Массовое удаление проекта и каскадное удаление комнат в первый этап не входят.

## 3. Разделение работы

### ChatGPT/Codex: пользовательский интерфейс и калькулятор

**A1. Подстановка площади.** Сохранённая площадь выбранного помещения подставляется в калькулятор и редактируется. В режиме размеров итог определяется геометрией. Новый расчёт без объекта не наследует предыдущую комнату. Существующий путь сохранения не ломается.

**A2. Экран проектов.** Поиск, список проектов, число комнат, прогресс расчётов, понятный следующий шаг. Создание проекта и добавление существующего помещения. Отдельная группа старых записей без проекта. Без финансовых итогов для монтажника.

**A3. Карточка проекта.** Клиент и адрес сверху; затем комнаты с названием, площадью, статусом и ответственными. Действия по комнате: диагностика, расчёт, документы. Общая сводка явно отделяет рассчитанные помещения от ожидающих расчёта. Один основной следующий шаг, остальные действия вторичны.

**A4. Главные страницы по ролям.** Компактная сводка задач и переходы в работу вместо одинаковой панели для всех. Используем только реальные доступные данные. Нет выдуманных сроков, конверсий, выручки и процентов.

**A5. Оформление.** Единая иерархия заголовков и кнопок; меньше служебного текста; понятные пустые состояния и ошибки; карточки удобны на телефоне; важное действие видно без длинной прокрутки. Новые блоки получают собственные стили, глобальную тему не переписываем.

### Грокбот: сервер, данные, документы, облако

**B0. Устойчивость после сбоя.** Уточнить исчерпанный лимит, проверить чтение и запись данных кабинета и запас места. Отделение материалов должно действительно исключать влияние их объёма на рабочие записи; новый бакет сам по себе не доказывает отдельную квоту. Возврат лимита только после проверки. Платные ресурсы и бюджет — решение Павла.

**B1. Проекты и сохранение.** Реализовать сущность проекта, серверные проверки компании и ролей, создание/редактирование/получение проектов, привязку помещений. Старый формат помещения остаётся совместимым. Сохранить новые поля в локальном хранилище и синхронизации, а не только в серверном ответе.

**B2. Передача между ролями.** Необязательные назначения менеджера, замерщика и монтажника по помещению. Старое назначение сохраняется как совместимый вариант, пока новые назначения не заданы явно. Добавить следующий шаг и срок. Монтажник получает только назначенные ему помещения; проект не раскрывает ему остальные комнаты и их суммы.

**B3. Документы и проверочный объект.** Владелец получает смету и спецификацию; монтажник только спецификацию. Завершить текущий скрипт тестового объекта, проверить реальный PDF. Не возвращать подстановку сметы монтажнику при отсутствии спецификации.

**B4. Материалы.** Завершить текущий перенос, реестр ошибок/дублей, подключение папок к обучению и серверные права. Предусмотреть выдачу больших файлов без передачи всего файла в base64 через ограниченный шлюз. Коммерческая политика — заглушка для владельца и STP до получения файла; остальные разделы независимы.

**B5. При наличии времени после рабочего контура.** Снимок общего предложения: состав помещений, использованные версии/снимки расчётов, количества и цены на момент формирования. Поздний пересчёт комнаты не меняет отправленное предложение. Полноценный PDF общего предложения — только после надёжного снимка, не вместо него.

## 4. Что видит каждая роль

| Роль | Главная задача экрана | Содержание |
|---|---|---|
| STP | Состояние сети и помощь партнёрам | Партнёры, активность за выбранный период, переход к компании, материалы. Число входов не называется продажами |
| Владелец | Управление проектами и командой | Проекты по этапам, предложения без следующего действия, неназначенные работы, предварительные суммы только рассчитанных комнат |
| Менеджер | Следующий контакт и предложение | Мои проекты/доступные проекты компании, следующий шаг и срок, диагностика, расчёты, документы |
| Замерщик | Выполнить замер | Назначенные и собственные доступные помещения, адрес, исходная жалоба, площадь/геометрия, переход в расчёт |
| Монтажник | Выполнить своё задание | Назначенное помещение, адрес, схема и спецификация без цен, разрешённая отметка выполнения |

Первый интерфейс может работать без полей срока/следующего действия: показывает честное «Не назначено», а не фиктивную задачу. После серверного этапа включает редактирование.

## 5. Единый контракт для независимой работы

Начальный контракт фиксируется здесь, реализация общих типов — только Грокботом:

- `Project`: `id`, `orgId`, `name`, `clientName`, `clientPhone`, `address`, `city`, `createdAt`, `updatedAt`, `createdBy`.
- Дополнительные поля `JobObject`: `projectId?: string | null`, `roomName?: string | null`.
- Следующий совместимый слой помещения: `salesUserId?`, `measurerUserId?`, `crewUserId?`, `nextAction?`, `dueAt?`. Идентификаторы сотрудников проверяются на принадлежность компании и подходящую роль; произвольные назначения не принимаются.
- API: `GET /projects` → `{projects}`, `POST /projects` → `{project}`, `PATCH /projects/:id` → `{project}`. Привязка комнаты через существующее обновление объекта с проверкой `projectId`.
- Отсутствующий серверный маршрут не считается успешным сохранением: интерфейс показывает недоступность функции, не маскирует её локальным демо.
- Клиентская точка доступа — новый `projectClient.ts`: `listProjects()`, `createProject(input)`, `updateProject(id,input)`. Сетевую/локальную реализацию делает Грокбот; ChatGPT использует её в экранах.
- Для назначения и следующего действия используется существующее сохранение объекта после поддержки новых полей сервером и синхронизацией.
- Названия/формат могут меняться только одной записью в этом контракте до интеграции. Нельзя независимо изобрести два формата проекта.

## 6. Точные границы файлов

**Только ChatGPT/Codex:**

- `apps/web/src/App.tsx`
- `apps/web/src/partner/PartnerContext.tsx` — калькулятор и клиентское подключение новых экранов; Грокбот не меняет этот файл параллельно.
- `apps/web/src/partner/CabinetScreen.tsx` — общая сборка экранов ролей, включая подключение готового компонента материалов.
- `apps/web/src/partner/ObjectsPanel.tsx` и компоненты истории при исправлениях.
- Новые `ProjectsPanel.tsx`, `ProjectDetail.tsx`, `RoleOverview.tsx`, их CSS-модули и тесты в `apps/web/src/partner/`.
- `apps/web/public/calculator/src/ui/app.js`, при необходимости `src/core/constants.js` и новые тесты подстановки.

**Только Грокбот и его агенты:**

- `apps/api/**`, `infra/**`, `packages/shared/partner.ts`.
- `apps/web/src/partner/apiClient.ts`, `localStore.ts`, `offlineDb.ts`, `syncEngine.ts`, новый `projectClient.ts` и их тесты.
- `MaterialsPanel.tsx`, `materialsClient.ts`, `MaterialStubView.tsx` и отдельные стили материалов.
- Скрипт тестового объекта, README, документация его запуска, при необходимости `package.json` и lock-файл. ChatGPT новые зависимости не добавляет.

**Важно:** прежнее разрешение Грокботу менять `CabinetScreen.tsx` этим планом заменено: теперь файл закреплён за ChatGPT. Материалы предоставляются отдельным компонентом; подключение делает ChatGPT. Общий `partner.module.css` не меняем параллельно — новые стили в CSS-модулях. При необходимой правке общего файла заранее меняется владелец конкретного участка.

Работа со скриптом калькулятора не должна менять его исходники: агент использует текущую версию для генерации PDF. Если изменение необходимо, его делает ChatGPT или участок передаётся последовательно.

## 7. Порядок без взаимного ожидания

**Блок 1, параллельно:** ChatGPT — подстановка площади и каркас проектов/страниц ролей по контракту; Грокбот — устойчивость хранилища, текущие материалы и серверные проекты через отдельного агента. Компоненты могут разрабатываться на локальных фикстурах, но не выдаются за готовую серверную функцию.

**Блок 2, интеграция:** серверные проекты, клиент доступа и сохранение полей → подключение интерфейса → проверка проекта с тремя комнатами. Материалы интегрируются независимо, без занятия файлов экранов.

**Блок 3:** назначения/следующее действие + интерфейс каждой роли. Если серверный слой не готов, сохраняем старые рабочие назначения и явно отмечаем недостающий новый сценарий.

**Блок 4, резерв:** снимок общего предложения, затем экспорт. Начинается только после работающего сохранения комнат и разграничения доступа.

Последние 60–90 минут доступной работы — только интеграция, исправления, развёртывание и проверка. Не начинаем новый большой блок в этот период. Оценка оставшегося объёма: 5–8 часов параллельной работы при доступном облаке; это ориентир, не гарантия. При блокере облака приоритет — проекты/сохранение и стабильность, а не объём загруженного видео.

## 8. Приёмка

1. Старые объекты и документы доступны после обновления. Ничего не сброшено.
2. В проект добавлены три разные комнаты; после перезагрузки состав сохранён.
3. Диагностика и расчёт относятся к правильной комнате, площади не смешиваются.
4. Неполный общий итог явно подписан; повторный расчёт не удваивает площадь/количество комнат.
5. Менеджер/замерщик/монтажник видят разрешённую работу. Компания не получает чужие проекты. Монтажник не получает цены через API, итог проекта, историю и PDF.
6. Владелец открывает оба вида документов, монтажник — только спецификацию.
7. Небольшой и крупный материал открываются на сайте; загрузка материалов не нарушает вход и сохранение проекта.
8. Проверены телефон и настольный экран, пустое состояние, ошибка сохранения и повторное открытие карточки.
9. История работает с раскрытием и сменой объекта.
10. Общее предложение считается готовым только при сохранённом снимке и воспроизводимом итоге; простая сумма текущих смет называется предварительной сводкой.

Статусы: реализовано → проверено локально → проверено на сайте. Зелёный деплой не заменяет сценарий. Не нужны повторные устные отчёты: обновление на GitHub только при готовом результате, блокере или изменении границ. Чужой PR не сливается без согласия Павла.
